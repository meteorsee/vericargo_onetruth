## Four Canonical Metric Definitions

**PASS with one finding.**

| Metric | Python (`metrics.py`) | SQL (`03_marts.sql` / `KPI_OVERVIEW`) | Semantic View (`05_semantic.sql`) | Consistent? |
|---|---|---|---|---|
| On-time delivery rate | `on_time / delivered` (actual ≤ promised) | `SUM(on_time_delivered_flag) / NULLIF(SUM(delivered_flag), 0)` | Same formula | Yes |
| Fill rate | `SUM(min(shipped, ordered)) / SUM(ordered)` | `SUM(capped_shipped_qty) / NULLIF(SUM(ordered_qty), 0)` | Same formula | Yes |
| Days of inventory | `on_hand / (trailing_30d_shipped / 30)` | Same | Same | Yes |
| Landed cost | `product + freight + duty + insurance + handling` | Same 5-component sum | `SUM(landed_cost_amount_usd)` | Yes |

**Finding — hardcoded expected values in `08_validation.sql`:** The metric validation checks compare against hardcoded constants (e.g., `0.6`, `590.0 / 610.0`, `68392.50`). These are correct for the current fixture but brittle — if the fixture changes, these checks silently fail. The Python tests use the same fixture data and independently compute the expected values, which is more robust. **No change needed** since the fixture is deterministic and intentionally frozen, but worth documenting.

### Issues found:

**Issue 1 — `AI_EXTRACT` response format:** In `04_documents.sql:106-118`, the `AI_EXTRACT` call uses a `responseFormat` parameter with field-level extraction prompts. The `AI_EXTRACT` function's `responseFormat` expects a JSON schema, not prompt strings. The current format (`'consignee': 'Extract the consignee name.'`) may work as informal guidance but doesn't follow the documented schema pattern. **Risk: medium** — this may work in practice since Snowflake's AI functions are flexible, but should be tested during deployment. If it fails, switch to proper JSON schema format.

**Issue 2 — `LEAST_IGNORE_NULLS` usage:** `04_documents.sql:124` uses `LEAST_IGNORE_NULLS()` which is a valid Snowflake function but relatively new. Verify it's available in the target account.

**Issue 3 — Dynamic table on dynamic table dependency:** `INVENTORY_METRICS` (`03_marts.sql:58`) depends on `ORDER_LINE_METRICS` (also a dynamic table). This is valid in Snowflake but all three dynamic tables share `TARGET_LAG = '1 minute'` and the same `VERICARGO_WH` warehouse. With XSMALL warehouse and three DTs refreshing every minute, there may be queuing. **Recommendation:** This is fine for a hackathon demo with small data volumes.

**Issue 4 — `SHIPMENT_RISK_FEATURES` is not a dynamic table:** The Snowpark procedure (`04b_snowpark_features.sql`) materializes `CURATED.SHIPMENT_RISK_FEATURES` via `write.mode("overwrite").save_as_table()`. This is a regular table that's only refreshed when the procedure is called. The semantic view references it as if it were always current. **This is acceptable** — the procedure is called during deployment and could be scheduled, but it means the risk features can go stale between refreshes. The daily task does not call this procedure.

**Issue 5 — Cortex Search `TARGET_LAG` on a view:** `06_actions_and_agent.sql:108-120` creates a Cortex Search service with `TARGET_LAG = '1 minute'` on `CURATED.DOCUMENT_SEARCH_CORPUS`, which is a view over `CURATED.DOCUMENT_PROCESSING` (a regular table). This is valid but the search index will only refresh when the underlying table changes.

**Issue 6 — Agent YAML `tool_not_accessible` field:** `06_actions_and_agent.sql:133` sets `tool_not_accessible: reject`. Verify this is a valid agent spec field — it should be, as it tells the agent to reject queries when tools are unavailable rather than hallucinating.

### No invalid SQL syntax found. All colon-prefixed variable references in procedures are correct (`:P_SHIPMENT_ID`, `:processed_count`, `:known_shipment_count`, `:new_case_id`).

## Unsafe Action Paths

**PASS — well guarded.** The `CREATE_REVIEW_CASE` procedure has five independent guards:
1. `P_CONFIRMED` must be TRUE (blocks agent hallucination)
2. Severity must be in allowed set
3. Reason must be 5-1000 chars
4. Source question must be 3-2000 chars
5. Shipment must exist exactly once

The agent spec instructs "Never infer confirmation" and "Pass the exact source question." The validation script (`08_validation.sql:131-139`) proves the guardrail blocks unconfirmed calls.

**One observation:** The procedure uses `EXECUTE AS CALLER`, which means it runs with the caller's privileges. This is correct for audit purposes (`CURRENT_USER()` captures the real actor) but means the caller needs INSERT privileges on `APP.REVIEW_CASES`.
